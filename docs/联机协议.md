# 联机协议

本文描述当前云端联机版实际使用的 HTTP 与 WebSocket 接口，依据工作区源码编写。它是本项目的协议，不是官方游戏服务器协议，也不表示全部官方行为已被完整还原。

发布版本为 **0.1.1**，传输协议版本为 **1**。两者分别来自 [shared/constants.js](../shared/constants.js) 中的 `APP_VERSION` 与 `PROTOCOL_VERSION`；[package.json](../package.json) 的版本号是发布版本。`hello.version`、`welcome.version`、`/healthz.version` 使用整数 `1`，`/healthz.app` 使用字符串 `"0.1.1"`。战斗规格的 `spec.v` 另由 [server/sim/spec.js](../server/sim/spec.js) 定义，目前也为 `1`。

2026-10-09（北京时间）公网联机验收已通过，原始记录见 [公网联机验证结果.json](../deployment/公网联机验证结果.json)，脚本见 [verify-public-network.mjs](../scripts/verify-public-network.mjs)。该次验收覆盖公网健康检查、两个独立会话、ping/pong、建房/加入/准备/开始、公共与私有状态同步、对局内断线恢复、推进到策略选择，以及退出后的房间与连接清理；它没有验证每一场完整战斗、所有难度或大规模并发。

## 1. 地址与 HTTP 资源

服务器默认监听 `0.0.0.0:3001`，可用 `HOST`、`PORT` 修改。浏览器默认连接当前页面同源的 `/ws`：

- HTTP 页面：`ws://<host>:<port>/ws`。
- HTTPS 页面：`wss://<host>/ws`，由部署入口提供 TLS 并转发 WebSocket。
- Node 服务自身使用 HTTP，HTTPS/WSS 由反向代理或隧道提供；部署方式见 [云服务器部署说明](../deployment/云服务器部署说明.md)。

HTTP 只接受 `GET`、`HEAD`，其他方法返回 `405`。没有账号注册、密码登录或存档写入的 HTTP API。

| 路径 | 返回内容 / 行为 |
| --- | --- |
| `/` | `public/index.html`，以及 `public/` 下的客户端文件 |
| `/assets/` 等公开静态路径 | 图片、音频、字体、模型等客户端资源 |
| `/data/` | `data/` 下的游戏数据 |
| `/shared/` | 浏览器与服务端共用的模块 |
| `/sim/` | `server/sim/` 下的 `.js` 战斗模拟模块；不提供 Node 专用 `nodeData.js` |
| `/data.js` | 服务端生成的浏览器数据模块适配代码 |
| `/healthz` | JSON 健康状态与进程内计数 |
| `/lan/room?code=ABCD` | 局域网房间探测；只对私网来源开放，只查询指定协作房间，公网请求返回 `404` |
| `/ws` | WebSocket 升级入口；其他升级路径返回 `404` |

`/healthz` 示例（计数和运行时长随服务状态改变）：

```json
{"ok":true,"version":1,"app":"0.1.1","uptimeSec":1551,"sockets":0,"sessions":0,"rooms":0,"matches":0,"humans":0,"bots":0}
```

其中 `sockets` 是当前 WebSocket 数量，`sessions` 包括重连窗口内的断线会话，`rooms`、`matches` 是房间与正在运行的对局数量，`humans`、`bots` 是房间中尚未永久离开的席位数量。因此关闭连接或退出房间后，`sessions` 不一定立即变为零。

静态资源支持 ETag、Last-Modified、条件请求、适用文件的 gzip 和单段字节 Range。HTML、代码和数据默认要求重新验证缓存。服务不提供目录列表，并拒绝路径穿越、点文件及受限模拟文件；实现见 [server/index.js](../server/index.js)。

## 2. 消息格式、请求编号与错误

WebSocket 应用消息使用 UTF-8 JSON 文本帧，顶层是对象，通过 `t` 区分类型：

```json
{"t":"room.ready","rid":4,"ready":true}
```

`rid` 可省略；提供时应是 `0` 至 `2147483648` 的整数。服务端成功响应通常为 `{"t":"ok","rid":4}`。`hello` 直接返回 `welcome`，`ping` 直接返回 `pong`，它们也回传有效的 `rid`。没有 `rid` 的成功操作通常只产生相关状态推送，不再单独返回 `ok`。

状态推送与请求响应是不同消息。例如建房时可先收到 `room.state`，再收到对应 `ok`；不能把 `ok` 当成完整房间或对局状态。`rid` 只关联本次请求，没有通用的重复请求去重功能。请求超时不代表服务端没有执行，尤其不要盲目重复购买等会改变状态的操作，应先核对重新同步的状态。

错误响应含 `code`、中文 `msg`，并可含有效 `rid` 与最多 120 个字符的开发诊断 `detail`：

```json
{"t":"error","code":"NOT_READY","msg":"仍有玩家未就绪","rid":5}
```

未知类型、无效字段、无效 JSON、二进制应用帧等返回 `BAD_MSG`；无法取得有效请求编号时，错误不含 `rid`。schema 未列出的字段不保证被校验或忽略，客户端只应使用本文和 schema 明确约定的字段。字段校验目录见 [shared/protocol.js](../shared/protocol.js)，错误代码及中文文本见 [shared/constants.js](../shared/constants.js)。

常见错误包括：

| 类别 | 代码 |
| --- | --- |
| 格式、限流与内部错误 | `BAD_MSG`、`RATE`、`INTERNAL` |
| 房间与权限 | `NOT_IN_ROOM`、`ROOM_NOT_FOUND`、`ROOM_FULL`、`ROOM_STARTED`、`NOT_HOST`、`NOT_READY` |
| 阶段、回合与玩家状态 | `WRONG_PHASE`、`NOT_YOUR_TURN`、`ALREADY`、`ELIMINATED` |
| 购买、装备与部署 | `NO_FUNDS`、`HAND_FULL`、`BOARD_FULL`、`BAD_TILE`、`BAD_TARGET`、`SOLD_OUT`、`MAX_LEVEL`、`TEMP_NOT_EMPTY` |

客户端 [public/js/net.js](../public/js/net.js) 的一般请求默认等待 8 秒，握手等待 8 秒。它另外产生 `TIMEOUT`、`OFFLINE`、`DISCONNECTED`、`CLOSED`、`REPLACED` 等本地错误；这些不是服务端的 `error.code` 枚举。协议版本不符时，服务端返回 `BAD_MSG` 和版本诊断，客户端显示刷新页面的提示。

## 3. 握手、身份与时间同步

建立 socket 后先发送 `hello`。昵称必须非空，输入长度上限为 12（按 JavaScript 字符串长度校验）；服务器还会规范化空白并清除控制、不可见字符等，再将接受后的名字放入 `welcome.name`。

首次握手：

```json
{"t":"hello","rid":1,"name":"博士甲","version":1}
```

返回示例：

```json
{"t":"welcome","playerId":"p_0123456789","token":"TOKEN_PLACEHOLDER","name":"博士甲","serverNow":1791480000000,"version":1,"resumed":false,"rid":1}
```

这里的 `TOKEN_PLACEHOLDER` 只是占位符，不能用于恢复真实会话。服务器产生随机公开 `playerId` 和秘密的 128 位随机 token（32 位十六进制字符串）；token 只发给所属玩家，不出现在其他玩家的房间席位中。

恢复握手使用此前的 token：

```json
{"t":"hello","rid":1,"name":"博士甲","token":"TOKEN_PLACEHOLDER","version":1}
```

- token 对应未过期会话时，保留 `playerId`，`welcome.resumed` 为 `true`，随后重发房间和当前对局状态。
- token 未知或已过期时，创建新身份，`resumed` 为 `false`，不会自动加入旧房间。
- `version` 在 schema 中可省略或为 `null`；提供非空值时必须等于 `1`。当前客户端始终发送协议号。
- 同一已绑定连接再次发送 `hello` 会更新会话昵称并请求状态重同步，不能通过换 token 切换身份；此时 `resumed` 不用于判断重同步是否发生。
- 同一 token 被新 socket 使用时，旧 socket 收到关闭码 `4001`（session replaced）。客户端会停止自动重连，避免两个页面不断互相替换。

服务端会话、token、房间和结果补发记录均在进程内存中，没有账号数据库或跨进程会话共享。服务重启后不能凭旧 token 找回席位。客户端通过 `sessionStorage` 保存本页 token，并用 `localStorage` 保存昵称和少量最近 token；同浏览器多页通过 BroadcastChannel 协调，尽量避免共用一个存活 token。浏览器保存的 token 不等于服务端持久存档。

应用层 `ping` 可以在 `hello` 前发送，用于延迟和时钟估计：

```json
{"t":"ping","c":1791480000000}
```

```json
{"t":"pong","c":1791480000000,"s":1791480000050}
```

`c` 是客户端发送时刻，`s` 是服务器处理时刻，均为毫秒时间戳。客户端用 `收到时刻 - c` 计算 RTT，用 `s + RTT/2 - 收到时刻` 估计服务器时间偏移；保留最近 8 个样本并采用最低 RTT 的样本。`welcome.serverNow` 和 `m.public.serverNow` 可提供初始时钟估计。该估计依赖网络时延，不能作为精确授时保证。

## 4. 房间生命周期

`mode` 为 `solo` 或 `coop`。`solo` 只允许一个真人、不允许机器人；`coop` 最多 4 席（真人与机器人合计），可以少于 4 席开始。难度枚举如下：

| 协议值 | 显示名称 |
| --- | --- |
| `FUNNY` | 标准模拟 |
| `NORMAL` | 险境模拟 |
| `HARD` | 绝境模拟 |
| `ABYSS` | 终极模拟 |

房间代码由 `ABCDEFGHJKLMNPQRSTUVWXYZ` 随机生成 4 个大写字母，加入时大小写不敏感。它是分享用的房间标识，没有密码或邀请权限校验。

典型流程，每一行都是一条独立消息；编号在各自连接中关联响应：

```json
{"t":"room.create","rid":2,"mode":"coop","difficulty":"NORMAL"}
{"t":"room.join","rid":2,"code":"ABCD"}
{"t":"room.ready","rid":3,"ready":true}
{"t":"room.start","rid":4}
```

建房、加入和席位变化会推送 `room.state`：

```json
{"t":"room.state","code":"ABCD","hostId":"p_0123456789","mode":"coop","difficulty":"NORMAL","inMatch":false,"seats":[{"seat":0,"playerId":"p_0123456789","name":"博士甲","isBot":false,"ready":false,"connected":true},null,null,null]}
```

`seats` 始终是 4 个槽位，空位为 `null`，`seat` 从 `0` 开始，成员离开后其他席位编号不前移。`inMatch` 表示房间是否有正在运行的对局。

- `room.ready {ready}`：等待房间中的真人切换就绪状态。
- `room.setDifficulty {difficulty}`：房主修改难度；变化后其他真人取消就绪。
- `room.addBot`、`room.removeBot {seat}`：仅房主可增删机器人，且只在协作房间等待阶段使用；机器人默认就绪。
- `room.start`：仅房主可开始，所有其他真人必须已连接且就绪；房主点击开始自身视为就绪。
- 已在等待房间时，成功建房或加入另一房间会隐式退出原房间；正在对局时须先 `room.leave` 或 `g.leave`。
- `room.leave`：退出当前房间。对局中会成为永久离开，不能通过该会话重连重新参战；席位在对局结束后释放。
- 房主离开或被移除后，由剩余真人接任，优先已连接且席位最靠前者。仅断线而仍保留席位时不会立即迁移房主。
- 没有尚未永久离开的真人时销毁房间，机器人不能单独保住房间。

`room.loadout {entries}` 保存干员技能与模组选择，key 为普通干员的棋子 ID，value 为含 `skill` 和/或 `module` 的对象；`module: "none"` 表示不装备模组，空 `entries` 表示使用默认选择。服务端按游戏数据检查干员、普通/精锐技能和精锐模组合法性，任何无效条目拒绝整条请求。它可以在房间外和等待阶段保存，并随会话进入后续房间；运行中的对局只在 `INFO_CHECK` 接受本局变更。之后提交会先保存为下局选择，再对本局返回 `WRONG_PHASE`，因此失败响应不表示会话中的下局选择完全没有改变。

## 5. 对局状态与操作概览

对局阶段名称由 [shared/constants.js](../shared/constants.js) 定义：`INFO_CHECK`、`BAND_DRAFT`、`BATTLE_CHECK`、`ROUND_START`、`SP_DRAFT`、`PREP`、`COMBAT`、`UNITE`、`SETTLE`、`FINAL_ASSAULT`、`HIDDEN_CORE`、`RESULT`。客户端依据服务器阶段与状态显示界面，不应只凭本地倒计时推断操作成功。

`m.public` 广播给房间中的真人，包含阶段、回合、`deadline`、`serverNow`、模式/难度、地图、策略禁用信息、玩家摘要、战场摘要、`combatMode`、`paused` 等；按阶段附加策略轮选、机变轮选、联防、共享 LP 和首领血池。`deadline` 为毫秒时间戳，`0` 表示该步骤没有倒计时。常规更新经过状态去重和约 100 毫秒节流，首领战中的公共摘要约每秒更新。

`m.private` 只发给对应真人，包含其资金、商店、奖励候选、整备区、临时整备区、棋盘、部署上限、羁绊、效果、下波敌人、干员调配和统计。它也经过状态去重，并在重连时强制补发。`m.public` 和 `m.private` 是当前状态视图，不是需要逐条累加的差量日志；相同字段应以最新视图为准。公开摘要、观战和战斗规格仍会提供相应战场的信息，`private` 不表示所有战斗内容对其他玩家绝对保密。

| 功能 | 客户端 → 服务端 | 服务端 → 客户端 |
| --- | --- | --- |
| 握手、延迟 | `hello`、`ping` | `welcome`、`pong`；失败为 `error` |
| 房间成员、准备、开始 | `room.create`、`room.join`、`room.leave`、`room.ready`、`room.start` | `room.state`、`room.closed`，以及请求 `ok/error` |
| 房主配置与机器人 | `room.setDifficulty`、`room.addBot`、`room.removeBot` | `room.state`、`ok/error` |
| 干员调配 | `room.loadout` | `ok/error`，本局适用时更新私有状态 |
| 信息确认、策略轮选 | `g.infoReady`、`g.band`、`g.bandSkip`、`g.bandFocus` | `m.public`、`m.private`、`ok/error` |
| 商店与棋盘 | `g.buy`、`g.refresh`、`g.freeze`、`g.levelUp`、`g.sell`、`g.move`、`g.equip`、`g.art`、`g.destroy` | `m.private`、`m.public`、`ok/error` |
| 奖励、机变与休整就绪 | `g.reward`、`g.choice`、`g.ready` | `m.private`、`m.public`、`ok/error` |
| 交流、观战与状态卡 | `g.emote`、`g.watch`、`g.unitStats` | `m.emote`、`m.field` 或 `b.start`、`m.unitStats`，以及 `ok/error` |
| 托管、单人暂停与退出 | `g.autoplay`、`g.pause`、`g.leave` | 对应状态变化、`ok/error`；暂停只限单人战斗 |
| 浏览器战斗 | `b.progress`、`b.result` | `b.start`、`b.pool`、`b.end`，以及适用的 `ok/error` |
| 提示与最终结算 | — | `m.toast`、`m.ticker`、`m.result` |
| 兼容的服务端流式战斗 | — | `m.field`、`b.snap`、`b.ev`（`SP_COMBAT=server`） |

操作的必填字段、坐标范围、枚举与可选字段应以 [shared/protocol.js](../shared/protocol.js) 为准。例如 `g.move` 使用 `uid` 和 `to`，目的地是 `{"area":"board","row":9,"col":2}` 或 `{"area":"hand","idx":0}`；方向可选，取 `UP/RIGHT/DOWN/LEFT`，省略时采用默认方向。`g.unitStats` 可传 `seq`，收到的 `m.unitStats {seq, round, units}` 用它区分先后请求，不等同于请求关联用的 `rid`。

## 6. 浏览器战斗协议

默认 `m.public.combatMode` 为 `"client"`：服务端管理房间、选人、商店、准备阶段和结算，发送战斗规格；浏览器运行共用的模拟模块。设置 `SP_COMBAT=server` 可切换到兼容的服务端模拟与快照流模式。

### `b.start`：开始或恢复一个战场

字段为 `battleId`、`fieldId`、`kind`、`spec`、`authoritative`、`startAt`、`serverNow`、`elapsed`、`speed`、`watch`、`done`。

- `kind` 为 `normal`、`unite`、`boss` 或 `hidden`。
- `battleId` 标识这一次战斗，客户端应原样用于上报，不要自行构造；它包含房间本局编号等区分信息，避免上一局迟到消息影响下一局。
- `spec` 是 JSON 安全的 BattleSpec，包括种子、地图、玩家单位、生成计划、路线、规则和适用的首领血池初值，具体构造见 [server/sim/spec.js](../server/sim/spec.js)。
- `authoritative: true` 才允许该客户端的战斗报告影响该战场；旁观副本只用于显示。普通战场通常由所属真人上报，共同战场优先选已连接且席位最靠前的真人。
- `startAt`、`serverNow` 为毫秒时间戳，`elapsed` 是已经过去的游戏秒数，`speed` 是模拟速度；恢复或观战时客户端按规格追赶到当前战场时间，而非接收每个单位的完整内存状态。

### `b.progress`：累积进度

必填为 `battleId`、`gt`（游戏秒）、`killed`、`total`。可选为 `leaks`、`bossDmg`、`by`、`done`、`left`。首领战使用累计 `bossDmg` 与玩家伤害分配 `by`，`leaks` 表示累计的团队 LP 扣除量；普通战斗的 `leaks` 表示漏怪计数。联防的 `left` 以漏怪来源玩家 ID 为 key，报告尚未清除的敌人数。

```json
{"t":"b.progress","battleId":"BATTLE_ID_FROM_B_START","gt":1,"killed":0,"total":5,"leaks":0,"done":false}
```

示例中的 battleId 和数量必须换成当前 `b.start` 与本地实际战斗的数据。当前客户端普通战场约每秒报告一次，首领战约每 250 毫秒一次，不带 `rid`。服务端对迟到、已完成或已撤销上报权的有效报告按无操作处理；不带 `rid` 的进度在对局刚结束时不产生错误提示。

### `b.result`：该场最终结果

使用 `{t, rid?, battleId, result}`。`result` 必须有 `reason`（`cleared/timeout/forced`）、`time` 和非空 `perPlayer`。每个玩家条目必须有 `killed`、`total`、`leaked`、`perfect`、`layerGains`、`unitsEnd`；其他统计、`unitStats`、联防的 `unspawned` 等按 schema 为可选。`unitsEnd` 的条目必须提供 `hpPct`、`sp`、`alive`，可含单位 `uid` 等身份信息。

客户端从实际模拟结果调用 `compactResult`、`fitResult` 后提交，具体见 [public/js/battle/runner.js](../public/js/battle/runner.js) 与 [server/sim/spec.js](../server/sim/spec.js)。不要用固定的示例结果代替真实战斗：服务端会核对规格中的玩家、敌人、漏怪来源与数量、羁绊层数、金币及单位归属等。结构不合法返回 `BAD_MSG`；结构合法但语义不可信时可返回 `ok` 并改用服务端重算或战场接管，因此 `ok` 只表示报告已处理，不保证原报告原样成为结算。

默认客户端战斗模式中，当前对局实例仍存在时，重复或过期的已完成 `b.result` 按无操作接受；整局结束、对局实例清理后，再提交结果可能返回 `WRONG_PHASE`。当前浏览器单次结果请求等待 15 秒，超时后重试一次；断线或再次超时的未送达结果会留在当前页面，在恢复在线或收到仍要求上报的同场 `b.start` 时重发。刷新页面会失去这份客户端内存，服务端仍可按自身接管策略完成战场。

### `b.pool` 与 `b.end`：共享血池与战场结束

`b.pool` 包含 `hp`、`max`、`teamLp` 和 `acked`，最多约每秒 4 次。`acked` 的 key 是 `fieldId`，value 是该战场已被服务端记账的累计首领伤害。客户端据此结合本地尚未确认的伤害显示首领血量，服务端共享池和团队 LP 决定最终结束条件。

```json
{"t":"b.pool","hp":900,"max":1000,"teamLp":100,"acked":{"b1":100}}
```

`b.end` 包含 `battleId`、`fieldId`、`reason`；`takeover` 表示原客户端停止上报，战场已被其他真人或服务端接管；`cleared`、`forced` 用于共享首领战的结束通知。

断线、结果超时或不可信结果会触发接管：普通与联防战场由服务端重新模拟规格，客户端结果的默认截止时刻是按速度换算的战斗时限结束后再加 15 秒；首领战优先交给同场伙伴，否则服务端接管。首领战超过 12 秒没有进度报告也触发移交。客户端观战副本和接管重算依赖相同规格、数据与模拟版本，不保证在网络或版本异常时每一帧画面完全一致。

## 7. 断线、重连与清理

| 情况 | 默认处理 |
| --- | --- |
| 客户端意外断线 | 指数退避重连：约 500 毫秒起，每次翻倍，上限基准 10 秒，附 ±20% 抖动；成功 `welcome` 后恢复在线 |
| 等待房间断线 | 席位保留 60 秒，期间显示 `connected:false`；超过宽限期释放席位，仍在会话重连窗口内返回时推送 `room.closed {reason:"timeout"}` |
| 协作对局断线 | 默认会话重连窗口 10 分钟，保留席位；战斗可被接管，计时阶段继续按对局规则推进 |
| 单人对局断线 | 会话窗口按 `data/config.json` 的 `singleReconnectTime` 延长，当前为 24 小时；无倒计时的休整/机变可等待返回，正在战斗可由服务器接管，并非所有阶段都暂停 |
| 会话窗口过期 | 移除会话；对局中按永久离开处理，等待房间中释放成员 |
| 显式 `room.leave` / `g.leave` | 永久离开；战斗中的退出按淘汰规则处理，剩余真人可继续；没有真人时结束并销毁房间 |
| 对局结束 | 房间回到等待状态，释放永久离开席位，真人取消就绪，清理对局实例；剩余成员可以再开一局 |
| 服务关闭 | 推送 `room.closed {reason:"shutdown"}`，WebSocket 以 `1001` 关闭，内存状态随进程结束消失 |

重连或重复 `hello` 会重发 `room.state`、`m.public`、自己的 `m.private`，并补发当前可见战场的 `b.start`；兼容流式模式补发相应战场与快照。重复 `hello` 的完整对局重同步按每会话至少间隔 1 秒合并，不应通过频繁握手拉取状态。

最终 `m.public` 和各真人的 `m.result` 会在内存中保留用于补发。对局结束后重连可再次看到结果，直到该玩家进行准备、修改难度/机器人、开始下一局或退出等房间操作；因等待宽限超时被移除的玩家，在其会话尚未过期时也可在 `room.closed` 后收到待补结果。这不是长期成绩存储。

服务端每 30 秒发送 WebSocket 控制 ping，未在下一次心跳前表现为存活的连接会终止；未发送 `hello` 的连接默认 30 秒后可被关闭为 `4002`，实际在心跳检查时触发。客户端另外每 4 秒发送应用 ping，在最早未获回应的 ping 之后超过 15 秒没有任何入站帧时主动重连；浏览器后台定时器节流会影响实际检查时机。

已发送的普通请求在 socket 丢失后被客户端拒绝为 `DISCONNECTED`，不会作为通用操作自动重放；重连期间尚未发送的请求可排队，仍受原请求超时限制，并在 `welcome` 后发送。

## 8. 限制与安全边界

以下是当前默认值，程序化启动选项可以覆盖部分网络和房间限制；环境变量与部署入口以实际部署为准。

| 项目 | 默认限制 |
| --- | --- |
| WebSocket 入站 payload | 64 KiB；不启用 per-message deflate |
| 每连接消息桶 | 每秒补充 40 条，突发容量 40 条 |
| 重型请求桶 | `g.watch`、`room.loadout` 另受每秒 2 条、突发 6 条限制 |
| 持续洪泛 | 一秒窗口内限流丢弃超过 400 条时以 `1008` 关闭 |
| 全局连接 / 会话 / 房间 | 2000 / 20000 / 1000 |
| 单公网网络连接 / 创建房间 / 启动中的对局 | 64 / 16 / 8 |
| 干员调配 | 最多 160 条，技能索引 `0–9`，还须通过游戏数据合法性检查 |
| 单场结果数组 / 映射 | 最多 4 玩家；每玩家 400 漏怪、64 单位结束状态、160 单位统计、40 羁绊增量；每漏怪最多 16 修正项；结果最多 400 未生成敌人，整体仍受 64 KiB 限制 |
| 下行积压 | 发送队列超过 16 MiB 终止连接；兼容流式模式的 `b.snap` 在超过 1 MiB 时可丢弃 |

网络额度按公网 IPv4 地址或 IPv6 `/64` 统计，可能由同一出口的多个玩家共享；无转发公网地址的本机/私网连接免于上述“单公网网络”额度，但仍受每连接限流和全局上限约束。WebSocket 升级超过单网络连接数返回 HTTP `429`，超过全局容量或正在关闭返回 `503`；房间或运行对局的单网络额度通常返回 `RATE`。

`TRUST_PROXY` 默认 `auto`，只在直接对端为回环/私网地址时采纳 `CF-Connecting-IP`、`X-Real-IP` 或最右侧 `X-Forwarded-For`。代理配置决定地址识别是否可靠；`TRUST_PROXY=1` 表示总是信任转发地址，不宜在可绕过代理直连的环境中使用。相关实现见 [server/net.js](../server/net.js)。

token 是持有即可恢复会话的秘密值，泄漏可能导致会话被替换；不要发布真实 token。当前直接 HTTP/WS 部署没有传输加密，应在公网部署入口启用 HTTPS/WSS。房间代码只有 4 位且没有密码，不能视为强身份验证或访问控制。

默认战斗采用客户端上报。服务端有结构校验、规格一致性与数值合理性检查、共享首领伤害/LP 记账预算、过期报告忽略和接管重算，但这些不等于完整反作弊。`SP_VERIFY` 默认 `off`；`sample` 对约八分之一的已接受普通/联防结果重算并记录差异，`all` 同步重算并在结果不同的时候采用服务端结果。首领战另按共享池与接管规则处理，不能将此开关理解为所有实时客户端行为都经过逐帧验证。

持久账号、跨服务器房间、进程重启后的恢复、正式排名与竞技级反作弊不在当前实现范围。后续调整消息字段或语义时，应同步检查 [shared/protocol.js](../shared/protocol.js)、[server/net.js](../server/net.js)、[server/lobby.js](../server/lobby.js)、[server/match/Match.js](../server/match/Match.js) 和 [public/js/net.js](../public/js/net.js)，并按兼容性需要更新协议版本。
